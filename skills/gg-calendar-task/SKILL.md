# 議事録からのカレンダータスク登録

## このスキルが解く問題

打ち合わせ後のタスク登録でよく起きる失敗は3つある。

1. **細かく入れすぎる。** 議事録の宿題を1件1予定にすると10件以上に膨れ、カレンダーが埋まって逆に見なくなる。
2. **タイトルが揃わない。** 後から検索・並べ替えできず、案件横断で追えない。
3. **説明欄が薄い。** 数日後の自分や、担当を振られた別のメンバーが読んでも何をすればいいか分からず、結局議事録を読み直すことになる。

このスキルはこの3つを防ぐ。

---

## 全体の流れ

1. 議事録・メール・メモを全文読む（要約や抜粋で済ませない）
2. 決定事項と宿題を抽出する
3. **統合して4〜6件に絞る**
4. 締切から逆算して日付を割り当てる
5. カレンダーの既存予定を確認する
6. 終日タスクとして登録する
7. 一覧を提示し、不確定事項を明示する

---

## 1. 元資料は必ず全文読む

文字起こしファイルは長く、`view` が中盤を省略することがある。省略された範囲に決定事項が入っていることが多いので、`view_range` を指定して読み飛ばした部分を必ず補う。

音声認識の文字起こしは誤変換が多い。特に社名・人名・専門用語は崩れる。文脈から推測できる場合は推測してよいが、**推測したことが分かるように書く**（後述の「要確認」参照）。

---

## 2. 抽出する対象

- 「〜します」「〜しておきます」と明言された宿題
- 「ちょっと考えてみます」「持ち帰ります」と保留になったもの
- 先方から依頼され、こちらが受けたもの
- 決定事項のうち、実行に作業が伴うもの
- 会話の最後に出た別件（雑談の流れで出た依頼は落ちやすい）

**決定事項そのものはタスクではない。** 「KPIはユーザー数にする」は決定であって作業ではない。「決定したKPIの目標数値を算出して提出する」が作業になる。

---

## 3. 粒度：統合して4〜6件に絞る

これが最も重要な判断になる。抽出した時点では10件以上あるのが普通だが、そのまま登録してはいけない。

**統合の基準は「同じ日に、同じ人が、まとめて着手できるか」。** できるなら1件にする。

| 統合してよい例 | 理由 |
|---|---|
| 数値の再集計 ＋ 目標値の算出 ＋ 競合調査 | すべて同じ資料に載せて提出する。分ける意味がない |
| イベント実装 ＋ 設定変更 ＋ 手順書作成 | 同じ作業セッションで片づく |
| 公開後の追加設定3件 | まとめて着手すればよい |

| 分けるべき例 | 理由 |
|---|---|
| 担当者が違う | 別の人に振るため |
| 締切が1週間以上離れている | 同じ日に置けない |
| 前工程の完了が前提 | 実装と検証は分ける |

目安は4〜6件。7件を超えたら統合が足りていないと考える。

---

## 4. 日付は締切から逆算する

公開日・提出期限・次回打ち合わせなど、動かせない日を起点に置く。そこから前工程を逆順に並べる。

```
8/18  サイト公開（動かせない）
 ↑
8/17  公開前の検証        ← 公開の前日
 ↑
8/13  実装作業            ← 検証までに数日の余裕
 ↑
8/6   資料の提出          ← 先方の社内報告に間に合う日
```

作業日ではなく**締切日**に置く。「この日までに終わっていればよい」という意味で使うほうが、予定が埋まっていても運用できる。

期限のないタスクは、関連する他のタスクの近くに寄せる。

---

## 5. 登録前にカレンダーを確認する

`list_events` で対象期間を見る。目的は2つ。

- その期間の稼働状況を把握する（詰まっている日を締切にしない）
- **既存の命名規則を確認する**。組織ごとに慣習があるため、既存の予定タイトルを見てから登録する

---

## 6. 登録の形式

### タイトル

```
【作業】会社名_作業名
```

- 会社名は正式名称（例：株式会社アマノ）。略称にしない
- 作業名は体言止めで簡潔に。「〜の修正」「〜の算出と提出」
- 全角スペースやカッコで飾らない

**例：**

```
【作業】株式会社アマノ_WordPress固定ページの修正
【作業】株式会社アマノ_KPI目標数値の算出と競合調査
【作業】株式会社アマノ_公開前の計測・リダイレクト検証
```

### イベント設定

```
allDay:       true
availability: AVAILABILITY_FREE
timeZone:     Asia/Tokyo
```

**`AVAILABILITY_FREE` は必須。** これがないとカレンダーが「予定あり」で埋まり、他の会議が入れられなくなる。タスクは締切の目印であって、時間の確保ではない。

### 色分け

| colorId | 色 | 用途 |
|---|---|---|
| 11 | トマト（赤） | 落とすと重大な影響が出るもの。公開前の必須作業など |
| 5 | バナナ（黄） | 自分の宿題。クライアントへの提出物 |
| 6 | みかん（橙） | 実装・設定作業 |
| 8 | グラファイト（灰） | 先方の判断待ち・こちらは案出しまで |

---

## 7. 説明欄のテンプレート

**この案件を知らない人が読んで着手できることを基準にする。** 数日後の自分も「知らない人」に含まれる。

```
■何をするか
（1〜2文。専門用語を使わず、何をする作業なのかを書く）

■なぜ必要か
（この作業が発生した経緯。誰が何と言ったのか。放置するとどうなるか）

■前提知識
（登場するツール名・専門用語を、知らない人向けに1行ずつ説明）

■作業の中身
（手順や項目。チェックリスト形式が使える場合は □ を使う）

■期限の理由
（なぜこの日なのか。何から逆算しているのか）

■担当
（自分以外が動く場合のみ）

■要確認
（不確定な点。確定していないことを書く）
```

すべての項目を埋める必要はない。ただし **「何をするか」「なぜ必要か」は必ず書く**。

### 書き方の注意

**専門用語はその場で説明する。** 説明を別の場所に置かない。

```
悪い例：
　GA4のキーイベントを設定する

良い例：
　GA4のキーイベントを設定する
　GA4はサイトに何人来て何をしたかを記録するGoogleの無料ツール。
　「キーイベント」に指定しないと、その行動は成果として集計されません。
```

**発言はそのまま引用する。** 要約すると温度感が失われる。

```
田中様「突き詰めるとキリがないので、やらないという判断も大事」
```

**数値は根拠として入れる。** 説明欄で完結させ、他の資料を開かなくて済むようにする。

```
検索エンジン経由のアクセスは12ヶ月で66,836セッション、全体の42.9%を占めます。
転送設定を誤ると、この4割を一気に失います。
```

---

## 8. 不確定なことは「要確認」として明示する

文字起こしの誤変換、会話が錯綜して結論が出なかった箇所、複数の解釈が成り立つ箇所は、**勝手に確定させない**。説明欄に候補を全部書き出し、確認が必要なことを明記する。

```
■要確認
競合3社が確定していません。会話では以下が候補に挙がりましたが、
錯綜したまま「じゃあその三社で」と締められています。

・アインズ&トルペ ← 「アオキよりこっちがいい」と明言。確定
・マツキヨ（「全国規模すぎるけど」と留保付き）
・スギ薬局
・名古屋ローカルの薬局（文字起こしでは「ラバイ」。ラブドラッグスの可能性）
```

推測で埋めると、後から誤りに気づいたときに手戻りが大きい。分からないことは分からないまま渡すほうが早い。

---

## 9. 登録後の報告

一覧表で提示する。

```
| 日付 | タイトル |
|---|---|
| 8/3(月) | 【作業】株式会社アマノ_WordPress固定ページの修正 |
| 8/6(木) | 【作業】株式会社アマノ_KPI目標数値の算出と競合調査 |
```

あわせて次の3点を短く添える。

- **日付の考え方**（何から逆算したか）
- **統合した点**（元は何件を何件にまとめたか）
- **要確認事項**（着手前に確定させるべきこと）

---

## 修正・作り直しの手順

`update_event` で個別に直せるが、**統合や粒度の変更を伴う場合は削除して作り直す**。中途半端に混ざると管理できなくなる。

1. `list_events` で対象期間の該当イベントIDを取得する
2. `delete_event` で削除する。`notificationLevel: NONE` を指定して通知を飛ばさない
3. 新しい構成で `create_event` する

削除件数と作成件数を報告に含める。
