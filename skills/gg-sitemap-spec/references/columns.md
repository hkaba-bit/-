## 2. 論理構造ブロック（A〜F列）

### ID

連番。行の識別子であり、議事録や見積書から参照するときのキーになる。
階層をまたいでも通し番号にする。番号を振り直さない（先方との会話で
「ID12の件」と言えなくなる）。

### 第1〜第4階層

**第1階層は6項目以内。** 7つを超えたら情報設計の失敗を疑う。

階層の書き方には2通りある。案件に合うほうを選び、シート内で統一する。

**A. 親行に第1階層、子行は第2階層以降だけ書く（推奨）**

```
ID  第1階層      第2階層          URL
2   ブライダル                    /bridal/
3               ダイヤの選び方    /bridal/diamond/
```

視覚的に階層が分かり、第1階層行に薄い背景色を付ければ塊が読める。

**B. 全行に第1階層を繰り返す**

フィルタや並べ替えを多用する運用なら、こちら。

### URL

全行に入れる。変数部分は `{slug}` のように書く。

- 末尾スラッシュ有無をシート内で統一する
- 絞り込みのクエリは `?purpose=xxx` のように実際の形で書く
- 新規ページも既存ページも同じ書式で書く

## 3. 見積ブロック（G〜T列）

### 構成（G〜J列）

情報設計・ワイヤーフレーム・原稿設計の工程。

| 列 | 意味 |
|---|---|
| TOP | TOPページの構成。ページ全体の方針を決める重い工程 |
| SP | SP版の構成を別途起こす場合 |
| 下層A / 下層B | 下層ページの構成。単価区分で分ける |

### デザイン（K〜N列）

| 列 | 意味 |
|---|---|
| TOP | TOPのデザイン |
| SP | SP版デザイン |
| 下層 | 下層ページのデザイン |
| フォーマット | テンプレート化（同型ページで流用する型を作る工程） |

**フォーマット列が重要。** ここに `■` が付く行の数がテンプレート数に近い。
制作費を決めるのはページ数ではなくテンプレート数なので、この列の合計を見れば
見積の妥当性が判断できる。

### コーディング（O〜T列）

| 列 | 意味 |
|---|---|
| TOP | TOPのコーディング |
| SP | SP対応 |
| 下層A / 下層B | 下層ページのコーディング。単価区分 |
| WP | WordPress化（投稿・カスタムフィールド・タクソノミの実装） |
| フォーム | フォーム実装（バリデーション・自動返信・確認画面） |

### 単価区分の差し替え

「下層A／下層B」は単価区分の想定。会社の単価表が別の区分（例：静的／動的、
S/M/L）なら列名を差し替えてよい。**差し替えたら凡例も必ず直す。**
列を増減する場合は入力JSONの `columns` を編集する。

## 4. 更新性（U列）

CMS化の範囲を決める列。**空欄で出さない。**

| 記号 | 意味 | 判断の目安 | WP列 |
|---|---|---|---|
| ◎ | 頻繁に更新 | 商品・記事・お知らせ。月1回以上 | ■ 必須 |
| ○ | 年数回の更新 | カテゴリトップ、価格帯、お客様の声 | ■ |
| △ | ほぼ更新しない | 会社概要、LP、コンセプトページ | 原則なし |
| × | 更新しない | 規約類、完了画面 | なし |

**◎○ の行数がWordPress化の工数**になる。ここを曖昧にしたまま見積を出すと、
公開後に「自分たちで更新できない」と言われて追加改修が発生する。

判定に迷ったら、**先方が誰の手で更新するつもりかを聞く**。
「更新したい」と「更新できる体制がある」は別物なので、体制がなければ△に落として
更新代行を保守契約に入れるほうが現実的なこともある。

色分けの目安：◎は赤系、○は青系。△×は無色。

## 5. 備考・根拠（V列）

このシートで最も価値が出る列。

**書くこと**

- そのページを作る根拠になる実測値
- 統合元のページ（「/history・/company・/message を統合」）
- ★差別化などの位置づけ
- 制作上の注意（「フォームは既存が静的HTML＋mail.php。WPへ載せ替え」）

**書き方の例**

```
良い： 現/archives/5683の受け皿（3ヶ月18,095セッション・来店予約0件）。広告の着地先をここへ
悪い： 重要なランディングページ。改善効果が期待できる
```

形容詞ではなく数字と固有名詞を使う。出所（GA4実測／Semrush推計／ヒアリング／
仮置き）が言えない数字は書かない。

## 6. 工程マークの付け方

マークは `■` で統一する。

### 原則

**付けない列があることが情報になる。** 全部に `■` を付けると、どこに工数が
集中しているかが読めず、見積として機能しない。

### 型ごとの目安

| ページの型 | 構成 | デザイン | コーディング |
|---|---|---|---|
| TOP | TOP・SP | TOP・SP | TOP・SP |
| カテゴリトップ／LP | TOP・SP | 下層・フォーマット | 下層 |
| 一覧（絞り込み付き） | 下層A | 下層 | 下層・WP |
| 詳細（商品・記事） | 下層A | 下層・フォーマット | 下層・WP |
| フォーム | TOP・SP | 下層 | 下層・フォーム |
| 完了画面 | – | 下層 | 下層 |
| 規約類 | 下層A | 下層 | 下層 |
| 絞り込みURL（noindex） | – | – | WP |

これは目安であって規則ではない。案件の作り方に合わせて調整する。

### 迷ったときの判断

- **同じ型のページが複数あるか** → あるなら1行目にフォーマットの `■`、
  2行目以降は下層のみ
- **既存ページの流用か** → 流用ならデザインの `■` を落とし、備考に「既存流用」
- **その工程が本当に発生するか** → 発生しないなら空欄。「一応付けておく」をしない

---

## 7. 集計行

データ行の下に1行空けて、工程別のCOUNTIFを置く。

```
=COUNTIF(G7:G26,"■")
```

**単価を横に掛ければそのまま見積になる**のがこのシートの存在理由なので、
集計行は必ず入れる。openpyxlは数式を文字列として書くだけでキャッシュ値を
持たないため、生成後に `recalc.py` を通す。

## 8. 付帯ブロック

シート下部に順に置く。

### 凡例

`■` の意味、更新性4段階の意味、単価区分の列名を差し替えた旨。
**列名を差し替えたら凡例も直す。** ここがずれていると読み手が混乱する。

### 制作対象外

据え置くページと、**その結果どうなるか**を書く。

```
ブランド固定ページ7本 ／ URL変更なし。旧デザインのまま残るため事前了承が必要
```

「据え置く」だけ書いて結果を書かないと、納品後に「思っていたのと違う」になる。

### URL移行

旧URL→新URL。件数を明記し、301の総数を書く。

```
/archives/ling/（249件） → /item/{slug}　※日本語URL＋全角スペースを整形
旧URL474件を全件301
```

リダイレクトマップの作成工数はここから積む。省略すると公開直後に自然検索が落ちる。

### 要確認事項

先方に決めてもらう項目。**工数の最大の変数を先頭に置く。**

```
1. 商品249件・記事131件のうち、移行対象は何件か（移行工数の最大の変数）
2. ブランド固定ページ7本を据え置きにして問題ないか
...
```
