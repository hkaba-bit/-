# 実装パターン集

型を決めた後に読む。該当する型だけ読めばよい。

---

## A. 費用シミュレーター

**使う場面**：予算が通るか不安／初期コスト削減を求められている／複数パターンの見積もり提示が要件

**解く問題**：一枚の見積書は「高い／安い」の二択しか生まない。
構成要素を分解して見せると、議論が「どこを削るか」に変わる。削る議論は
発注前提の議論であり、そこに入れた時点で受注は近い。

### 構成

```
[ 上部 ] フェーズ切替（第1期 / 第2期 / 第3期）またはプラン切替（松 / 竹 / 梅）
[ 中央 ] 選択中の構成内訳（項目・金額・必須/任意のバッジ）
[ 下部 ] 初期費用合計 / 月額合計 / 3年総額
[ 脇   ] 「この構成で実現できること / 見送るもの」
```

### 操作要素

- スコープのオン/オフ（チェックボックス。任意項目のみ）
- フェーズまたはプランの切替（タブ）
- ページ数・記事数などの数量スライダー（あれば1つだけ）

### 必ず入れる

- **任意項目を外したときに「何ができなくなるか」の表示**。金額だけ下がる
  シミュレーターは、削っても平気だと誤解させる
- 段階導入の場合、次フェーズに送った項目が消えずに「第2期へ」と残ること
- 3年総額。初期費用だけ見ると保守費の議論が抜ける

### やらない

- 全項目をオン/オフ可能にすること。必須項目は固定して外させない
- 最安構成をデフォルトにすること。推奨構成を初期表示にする

## B. 施策マトリクス

**使う場面**：何から着手するか／段階的に進めたい／リニューアルまでの繋ぎで今できることを知りたい

**解く問題**：施策一覧は「全部やるか、やらないか」を迫る。
効果と工数の2軸に置くと、優先順位の議論になる。

### 構成

```
[ 上部 ] 2軸マップ（横：実施ハードル / 縦：期待効果）に施策をプロット
[ 中央 ] 施策をクリックすると詳細（内容・期間・費用感・前提）
[ 下部 ] 選択した施策の合計（期間・費用レンジ）
[ 脇   ] フェーズ別のロードマップ表示
```

### 操作要素

- 施策のクリック/選択
- フィルタ（自社対応可 / 要外注、短期 / 中期）
- フェーズ切替

### 必ず入れる

- **「今すぐ着手できるもの」の明示**。予算未計上の案件では、
  無料または低額で始められる施策が入口になる
- 各施策の前提条件（この施策はCMSがWordPressであること、など）
- 施策間の依存関係。Aをやらないと B ができない場合は矢印で示す

### やらない

- 全施策を高効果に置くこと。効果が低い施策も正直に配置したほうが信用される
- 工数を隠すこと。ハードルが高い施策はそう見せる

## C. 競合比較ダッシュボード

**使う場面**：競合に埋もれている／差別化できているか不安／ベンチマーク企業が明確

**解く問題**：「御社は競合に負けています」は反発を生む。
同じ項目で並べて、事実として差を見せると、課題が共有される。

### 構成

```
[ 上部 ] 比較軸の選択（情報量 / 導線 / 訴求 / SEO / 更新頻度）
[ 中央 ] 自社 + 競合3〜4社の比較表またはレーダーチャート
[ 下部 ] 差が大きい項目の抜き出しと、そこへの打ち手
```

### 操作要素

- 比較軸の切替
- 競合の表示/非表示
- 自社の「現状」と「リニューアル後」の切替トグル

### 必ず入れる

- **評価の基準**。「情報量：3」ではなく「サービス詳細ページ数：自社4 / A社18」
  のように、誰が数えても同じ数字になる指標を使う
- 出典と調査日。競合サイトは変わる
- 自社が勝っている項目。全項目で負けている比較表は、
  作為を疑われるか、単に相手を落ち込ませるだけになる

### やらない

- 主観評価（デザインの良し悪しなど）を数値化すること
- 競合の実名を出さない配慮。ヒアリングで先方が挙げた社名はそのまま使う

## D. 効果試算

**使う場面**：投資対効果を説明する必要がある／決裁者にマーケ理解がない／KGIが数値

**解く問題**：Web施策の効果は決裁者にとって最も疑わしい部分。
計算過程を全て見せることで、数字ではなく**ロジック**を評価してもらう。

### 構成

```
[ 上部 ] 入力（現状のセッション数 / CVR / 客単価 / 商談化率）
[ 中央 ] 計算過程を段階表示（セッション → CV → 商談 → 受注）
[ 下部 ] 想定効果のレンジと、投資回収期間
```

### 操作要素

- 現状値の入力（3〜4項目。ヒアリング値を初期値にする）
- 改善率の想定（保守的 / 標準 / 楽観 の3段階トグル）

### 必ず入れる

- **計算過程の全表示**。結論の数字だけ出すと信じてもらえない
- 保守的ケースでも投資回収できるか。楽観ケースだけ見せない
- 前提条件の明示（この試算は現状の商談化率が維持される前提、など）
- レンジ表示。単一値は出さない

### やらない

- 業界平均CVRを根拠にすること。出所を聞かれて答えられない
- 施策の効果を足し算すること。施策は掛け合わせでも相殺でもある

## E. 体験デモ

**使う場面**：提案する機能のイメージが湧かない／検索UI・診断・シミュレーターなどを提案に含む

**解く問題**：機能は言葉で説明しても伝わらない。触れば3秒で伝わる。

### 構成

```
[ 上部 ] 「これは提案する機能の動作イメージです」の明示
[ 中央 ] 実際に動く機能（ダミーデータで可）
[ 下部 ] 実装時の想定（工数・前提・できないこと）
```

### 操作要素

- 提案する機能そのもの

### 必ず入れる

- **これがデモであることの明示**。完成品と誤解されると期待値がずれる
- ダミーデータは業種に合わせた現実的な内容にする。「サンプル1」では伝わらない
- 実装時の制約。デモでできて実装で難しいことは先に言う

### やらない

- デザインを作り込むこと。デモは動作を見せるもので、意匠の合意を取る場ではない
- 本番同等のデータ量を入れること。動作が重くなり商談が止まる
