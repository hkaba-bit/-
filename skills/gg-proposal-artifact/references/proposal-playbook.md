# 商談での見せ方とチェックリスト

---

## 提案書（PPTX）との役割分担

| 媒体 | 役割 |
|---|---|
| PPTX | 提案の論理構造。持ち帰って社内回覧される。**これが正本** |
| Artifact | 商談中の合意形成。触ってもらう。回覧されない前提 |

**Artifactだけで提案しない。** 決裁は持ち帰った資料で行われる。
商談に出席していない役員が見るのはPPTXであり、そこに情報がなければ落ちる。

### PPTXへの落とし込み

1. Artifactの主要3パターンを静止画キャプチャして貼る
   （推奨案 / コスト最小案 / 最大案 など）
2. キャプチャの下に、そのパターンの結論を1行で書く
3. 「商談で実際に条件を変えてご覧いただけます」と注記
4. 送付時はArtifactの共有リンクを添える

キャプチャは**推奨案を最初**に置く。シミュレーターは動かせるが、
資料は動かないので、こちらが見せたい順に並べる。

## 商談での運用

### 見せる順番

1. まずPPTXで論理を通す（課題 → 方針 → 具体策）
2. 費用や優先順位の話になった時点でArtifactを開く
3. **先方の条件を聞きながらその場で入力する**
4. 出た結果を起点に議論する
5. 商談後、その場の条件で確定した内容をメールで送る

冒頭からArtifactを見せない。文脈がない状態で数字を見せると、
金額の話だけになって提案の中身が伝わらない。

### 触ってもらうきっかけ

こちらが操作し続けると「見せられている」ままになる。
以下の言い方で相手の手に渡す。

- 「御社の現状だとこのあたりですよね、変えてみていただけますか」
- 「この項目、御社なら社内対応できそうですか。外してみます」
- 「予算の上限を入れると、どこまで入るか出ます」

### 想定される質問への備え

| 質問 | 備え |
|---|---|
| その数字の根拠は | 画面内に出所を書いておく |
| 他社ならいくらか | 答えない。自社の構成の妥当性で話す |
| もっと安くできないか | 削る項目とその影響がその場で出せる状態にしておく |
| 本当にこの効果が出るのか | 保守的ケースを見せる。レンジで話す |

## 品質チェックリスト

提出前に全項目を確認する。

### 動作

- [ ] 極端な値（0、上限値、空欄）を入れて NaN / Infinity / エラーが出ない
- [ ] 全ての操作要素を1回ずつ動かした
- [ ] 初期状態に戻せる（リセット手段がある、または再読込で戻る）
- [ ] `localStorage` / `sessionStorage` を使っていない
- [ ] 数値の丸めが正しい（合計が内訳と1円単位でずれていない）

### 内容

- [ ] 全ての数値に出所が書かれている
- [ ] 仮置きの数値に「仮」の表示がある
- [ ] 税別／税込が明示されている
- [ ] 初期費用と月額が混在していない
- [ ] 効果予測がレンジで示されている
- [ ] 前提条件が画面内に書かれている
- [ ] 初期値が先方の現実の条件になっている

### 見せ方

- [ ] 1画面に収まっている（スクロールが必要な場合は主要部が上部にある）
- [ ] 結果の数値が32px以上
- [ ] 画面共有を想定した文字サイズ（16px以上）
- [ ] 有彩色が「動く数字」と「推奨案」に限定されている
- [ ] 操作要素が5個以下

### 提案全体

- [ ] PPTXに静止画が入っている
- [ ] 推奨案が最初に見える状態になっている
- [ ] 「削る議論」ができる状態になっている
- [ ] 案件ファイル `/areas/{案件名}.md` に作成記録を追記した

## やってはいけないこと

**都合のいい初期値**
デフォルトが高額プランや楽観ケースだと、動かした瞬間に不信感が出る。
初期値は先方の現実の条件にする。

**削れない設計**
必須項目しかないシミュレーターは、単なる見積書の焼き直し。
削る余地を見せることが、この道具の価値。

**競合を落とす比較**
劣る側を赤で塗る、主観評価を数値化する、といった作為は見抜かれる。
事実の並列に徹する。

**回覧されない前提の情報**
Artifactにしか書いていない重要情報があると、決裁の場で消える。
結論は必ずPPTXにも書く。
