# 提案用インタラクティブ資料の構築

## このスキルが解く問題

提案書（PPTX）は静止画である。静止画で費用や施策の選択肢を示すと、
クライアントは「書かれた案」を評価するだけで、**自分の条件で考えない**。

商談中に条件を変えて結果が動くものを見せると、議論が
「この会社の案は妥当か」から「うちならどう組むか」に変わる。
そこまで持ち込めた会社が受注する。

このスキルは、案件の論点に応じた1点を短時間で組み、
画面共有で触りながら合意を取るための道具一式を提供する。

**1案件1アーティファクトが原則。** 複数作ると商談の焦点がぼやける。
提案の勝ち筋そのものを1つ選んで、そこに密度を集中する。

## 参照ファイル

作業に入る前に、該当するものを読む。

| ファイル | いつ読むか |
|---|---|
| `references/artifact-patterns.md` | 型を決めた後、実装に入るとき（毎回） |

## ワークフロー

### STEP 1. 与件から論点を1つに絞る

案件資料・ヒアリング議事録から以下を拾う。埋まらない項目は推測で埋めず、
「要確認」として明示し、提案時の質問として残す。

| 項目 | 確認すること |
|---|---|
| 決裁の壁 | 誰が何を根拠に承認するか。予算会議か、役員か、社長か |
| 予算の状態 | 上限額／未計上／削減余地を求められているか |
| 先方が繰り返した言葉 | 議事録で2回以上出た不満・要望。これが論点 |
| 提出物の指定 | RFPで名指しされた成果物があるか |
| 競合状況 | コンペか随意か。相手が何を出しそうか |
| 判断時期 | いつ何が決まるか。その場で決まるのか持ち帰りか |

**論点は1つに絞る。** 「予算も体制もSEOも心配」は論点ではない。
先方が最も繰り返した1つが論点であり、それがアーティファクトの型を決める。

### STEP 2. 型を判定する

| 論点 | 作る型 |
|---|---|
| 予算が通るか／初期コストを下げたい／複数パターンが欲しい | **A. 費用シミュレーター** |
| 何から着手するか／段階的にやりたい／今できることを知りたい | **B. 施策マトリクス** |
| 競合に埋もれている／差別化できているか不安 | **C. 競合比較ダッシュボード** |
| 投資対効果が説明できない／役員にマーケ理解がない | **D. 効果試算** |
| 提案する機能のイメージが湧かない | **E. 体験デモ** |

判定に迷ったら **「決裁者が承認できない理由」** を書き出す。
それを潰す型を選ぶ。決裁者が予算を心配しているのに競合比較を出しても刺さらない。

複数該当する場合は、**決裁の壁に最も近いもの**を優先する。
予算会議が控えているならA、役員説得ならD。

### STEP 3. 数字と項目を確定する

実装前に、扱う数値の出所を全て確定させる。ここを飛ばすと
「それは何の数字ですか」で商談が止まる。

```
【使う数値】
項目：
値：
出所：（ヒアリング/公開情報/GrowGroup実績/仮置き）
仮置きの場合の根拠：
```

**出所が言えない数字は載せない。** 仮置きが避けられない場合は
画面上に「仮」と明示し、実データへの差し替え前提であることを口頭で言える状態にする。

金額は必ず税別・税込を明示する。月額と初期費用を混在させない。

### STEP 4. 実装する

1. `references/artifact-patterns.md` の該当パターンを読む
2. `assets/_artifact-template.html` を起点にする
3. 操作要素（スライダー・トグル・チェックボックス）を3〜5個に絞る
4. 結果表示は数値だけでなく**構成の内訳**まで見せる
5. 「なぜこの数字になるか」の根拠を画面内に併記する

**操作要素を増やしすぎない。** 触れる箇所が多いと、商談中に
説明が必要になり本題が進まない。動かすのは論点に直結する軸だけ。

### STEP 5. 検証する

`proposal-playbook.md` の品質チェックリストを全項目確認する。
特に **極端な値を入れて破綻しないか** を必ず試す。
商談中に「0」や上限値を入れられて NaN が出ると信頼を失う。

### STEP 6. 提出する

提案書（PPTX）には静止画キャプチャを載せ、Artifactは商談で開く。
PPTXへの落とし込み方は `proposal-playbook.md` を参照。

## 実装の規約

### 絶対に守る3点

1. **`localStorage` / `sessionStorage` を使わない**（Artifact環境で動かない）
2. **操作要素は5個以下**
3. **数字の出所を画面内に書く**

### 見せる相手を想定する

商談は画面共有かプロジェクタ。手元のPCで見るものではない。

- 基本フォントは16px以上。結果の数値は32px以上
- 1画面に収める。スクロールさせると共有画面で迷子になる
- 操作した結果が**同じ画面内で**変わること。画面遷移させない

### 色

有彩色は「動く数字」と「推奨案」にだけ使う。それ以外は無彩色。
色数が増えると、どこを見ればいいか分からなくなる。

比較で優劣を示すときも、劣る側を赤にしない。
提案は他社批判の場ではなく、**選択肢の提示**の場である。

### 数字の扱い

| やること | やらないこと |
|---|---|
| 幅を持たせる（300〜400万円） | 断定的な単一値 |
| 前提条件を併記 | 前提なしの試算 |
| 「仮」の明示 | 仮置きを実数のように見せる |
| 出所の明記 | 出所不明の業界平均 |

**効果予測は必ず幅とレンジで示す。** 単一値を出すと、
達成できなかったときに提案そのものの信頼が崩れる。

### 触ってもらう設計

初期値は**先方の現実の条件**にしておく。
デフォルトが自社に都合のいい条件だと、動かした瞬間に不信感が出る。

推奨案には理由を添える。「弊社おすすめ」ではなく
「御社の◯◯という条件ではこの構成が最も投資対効果が高い」と書く。

## 案件ファイルとの連携

`/areas/{案件名}.md` に案件情報がある場合は、STEP 1 の前に必ず読む。
論点・予算・決裁フロー・競合はそこに記録されている。

作成後、その案件ファイルに以下を追記する。

```
- [stated] 提案用Artifact「{型}」を作成（{日付}）
```
