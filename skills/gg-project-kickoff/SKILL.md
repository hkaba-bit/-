# 案件キックオフ（gg-project-kickoff）

## このスキルが解く問題

案件が出るたびに、与件集めと成果物づくりを毎回ゼロから組み立てている。
集める順番・渡す情報・検品の観点が人によって変わり、**下流の成果物が食い違う**。

このスキルは**立ち上げの型**。何を良しとするかの判断基準は `gg-proposal-standard` が持つ。

---

## 1. 回す案件・回さない案件

gg-manager の案件JSON（`projects_fetch`）の `type` と `projectTypeRule` で判定する。

| 条件 | 扱い |
|---|---|
| `type` が **「Webサイト制作」で始まる** | **一式を回す** |
| `projectTypeRule` が `R6:new-build` | 同上 |
| 上記以外（サイト修正・広告運用・保守・レポート） | **回さない。**ページ単位の作業であって設計工程がない |

> 直近15件の受注案件のうち、この条件に当たるのは1件だけだった（2026-09-18 時点）。
> **全案件で回すと小規模修正まで巻き込んで無駄になる。**必ず絞る。

判断に迷ったら回さない。人間に聞く。

---

## 2. 手順

### Phase 0：案件ディレクトリを作る（機械的）

```bash
# gg-manager の projects_fetch の出力をファイルに保存してから
python3 scripts/kickoff-project.py --slug <案件スラッグ> --json <案件.json>
```

スラッグは**ドメイン名から取る**のが最も安定する（`johokusaitama.ac.jp` → `johoku-saitama`）。
既にディレクトリがあれば何もしない。上書きしない。

`research/brief.md` に、会社名・担当・金額・Backlog・Dropbox・Zoho が自動で入る。
**判断が要る欄は空のまま出てくる。**次でそこを埋める。

### Phase 1：与件を集める（単独でやる。分割しない）

下流が全部これを土台にするので、**ここがブレると全部やり直しになる**。

| # | 集めるもの | 取り方 |
|---|---|---|
| 1 | 受注条件 | Backlog 課題の本文（設計ページ数・デザイン対象・流し込み記事数・システム・外注可否・納期） |
| 2 | ヒアリング | Dropbox `/GrowGroup/GrowMeet/` 配下の要約・文字起こし |
| 3 | 既存の仕様書・提案書 | Backlog 本文の Dropbox リンク。**シートごとに「埋まっているか」を確認する** |
| 4 | 現行サイト | `site_crawl`（深度3・200ページ）＋ `http_headers` ＋ トップの HTML ソース |

集めたら `research/brief.md` と `research/current-site-audit.md` に書く。

**3つの論点は必ずここで確定させる。**ヒアリングで2回以上出た言葉から取る。
4つに増やさない。これが決まらないうちは Phase 2 に進まない。

### Phase 2：並列セッションに分割する

Phase 1 を commit & push してから、クラウドセッションを3本起動する。
**会話履歴は渡さない。**渡すのは Goal / Context / Constraints / Done-when の4点だけ
（`references/role-split.md` の引き渡しの型）。各セッションは `brief.md` を読んで動く。

| セッション | 成果物 | ブランチ | 主に使うスキル |
|---|---|---|---|
| 仕様書 | サイトマップ Excel・URL移行ブロック | `claude/<slug>-sitemap-spec` | `gg-sitemap-spec` |
| ワイヤー | index＋主要ページのクリッカブルHTML | `claude/<slug>-wireframe` | `gg-wireframe` |
| 提案書 | 骨子→原稿→PPTX | `claude/<slug>-deck` | `gg-proposal-deck` |

全セッションに共通で入れる制約：

- AGENTS.md 準拠
- **数値を創作しない。**未取得のものは「未取得」、推定は「推定」と明記する
- 見積金額はスライドに書かない（反映先D＝見積書側）
- 固定ブロック（`fixed-blocks.md`）は触らない
- 各自 PR を作り、本文に「判断した点」と「人間の確認が要る点」を箇条書きで書く

### Phase 3：回収して検品する（実装した側に検品させない）

25〜30分後にチェックインを入れ、PR を検品してから統合する。

| 観点 | 見るもの |
|---|---|
| 規約違反 | クライアント実名・見積金額の混入（`AGENTS.md` 第3章） |
| 数値の創作 | 出典のない数字、レンジでない効果予測、「推定」の欠落 |
| 論点の一貫性 | 3つの論点が P2・P5・各章で一致しているか。参照列が実際の章番号と合っているか |
| 成果物の自己検証 | `verify_sitemap_xlsx.py` / `qa-wireframe.py` / `validate.py` が通っているか |
| 抜け | `check-skill-assets.py`・`check-skills-table.py` |

検品で直すべき点が出たら、**実装したセッションに差し戻す**（`SendMessage`）。自分で直さない。
統合したら `STATUS.md` の「進行中の案件」表を更新する。

## 3. 渡し方のテンプレ

```
Goal: <1〜2行。何を達成したいか>

Context:
  - 与件: projects/<slug>/research/brief.md（必ず最初に読む）
  - 現行サイト調査: projects/<slug>/research/current-site-audit.md
  - 規約: skills/<該当スキル>/SKILL.md
  - 出力先: projects/<slug>/<サブディレクトリ>/

Constraints: AGENTS.md 準拠。<今回固有の制約>。数値を創作しない

Done when: <検証方法まで書く>。ブランチ claude/<slug>-<用途> に push し PR を作る
```

---

## 4. やってはいけない

| NG | なぜ |
|---|---|
| 与件が固まる前に分割する | 3本が別々の前提で走り、全部やり直しになる |
| 全案件で一式を回す | 小規模修正・広告運用には設計工程がない。時間と費用の無駄 |
| 会話履歴をセッションに渡す | 渡すはずのないトークンを払うことになる |
| 実装したセッションに検品させる | 同じ思い込みを二度通すだけ |
| 受注済み案件に新規提案書を作る | 提出・承認済みのものと重複する。**まず商談ステージを確認する** |
| 数値目標をサンプル値のまま出す | 既存仕様書はテンプレートのまま空欄のことが多い。GA4 実数を取ってから埋める |
