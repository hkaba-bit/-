# 提案書フォーマット（gg-proposal-deck）

## このスキルが解く問題

提案書の構成・粒度・言い回しが作成者の頭の中にある。日拓提案（118P）が事実上の到達点だが、
型として共有されていないため、プロデューサーごとに章立てと密度がばらつく。

このスキルは**骨格の正本**。何を良しとするかの判断基準は `gg-proposal-standard` が持つ。

## 参照ファイル

| ファイル | いつ読むか |
|---|---|
| `references/structure.md` | 骨子を組むとき（章別スライド定義・全118Pの型） |
| `references/copy-rules.md` | 原稿を書くとき（版面・文言・数字の規約） |
| `references/policy-rules.md` | **毎回必ず**（特記事項＝社内の政策ルール） |
| `references/fixed-blocks.md` | 章13〜19の確定文言が要るとき |
| `references/variants.md` | 案件類型で章を増減させるとき |

## 最初にやること（順番厳守）

1. `references/policy-rules.md` を読む。**未反映のルールがある状態で提案書を出さない**
2. `gg-proposal-standard` の与件整理表を埋める（決裁の壁／論点／提出物指定／競合状況）
3. **3つの論点を確定させる**。これが決まらないうちは1枚も書かない
4. 案件類型を `references/variants.md` で判定し、章の増減を決める
5. モードを選ぶ（下記）

## 3つのモード

| モード | 入力 | 出力 | 使う場面 |
|---|---|---|---|
| **A. 骨子** | 議事録・RFP | 章立て＋全スライド一覧（Markdown）＋想定P数 | 着手時。社内合意用 |
| **B. 原稿** | 確定した骨子 | スライド1枚ごとの ヘッダ／タイトル／リード文／要素／出典 | 骨子承認後 |
| **C. PPTX** | 原稿（`deck.json`） | PPTXファイル | 作業用ドラフト。意匠仕上げはCanva |

指定がなければ **A → B** の順に進め、Cは明示的に求められたときだけ実行する。

### モードC（PPTX生成）の位置づけ

正本PPTXはCanva書き出しで、スライドごとに画像を敷き込んだ自由組版。**pptxgenjsで意匠は再現しない。**
モードCが出すのは「版面規約に沿った構造的に正しい作業用ドラフト」。
用途は ①社内レビュー ②Canva作業の下書き ③ページ数と情報量の事前確認。
先方提出物としてそのまま使わないこと。

```bash
# 作業ルート（AGENTS.md がある階層）から実行する
node skills/gg-proposal-deck/scripts/build_deck.js deck.json out.pptx
python "$(python scripts/find-skill-script.py pptx scripts/office/validate.py)" out.pptx
```

`deck.json` の書式は `assets/deck-schema.md`、雛形は `assets/deck-example.json`。

### テンプレートPPTX

`assets/deck-template.json` は**81枚のテンプレート**の定義。
固定ブロック（章13〜19）は確定文言入り、可変ブロックは `〔　〕` のプレースホルダ。

```bash
node skills/gg-proposal-deck/scripts/build_deck.js skills/gg-proposal-deck/assets/deck-template.json テンプレート.pptx
```

新規案件では、このPPTXを複製して `〔　〕` を埋めていくのが最短。
`〔` が残っていないか、提出前に必ず検索して確認する。

### 区分の意味

| 区分 | 枚数 | 扱い |
|---|---|---|
| 可変（P2–P51） | 約50P | **毎回ゼロから書く。ここが主戦場** |
| 半可変（P52–P90） | 約39P | 要否判断＋数値差し替え。既存ライブラリから選ぶ |

**時間配分もこの比率に従う。** 固定ブロックの推敲に時間を使わない。

## 一貫性ルール（このフォーマットの核）

正本は **P2サマリー → P5「3つの論点」 → 各章** が同じ3本の軸で貫かれている。
章立てより、この一貫性のほうが再現価値が高い。

| ルール | 内容 |
|---|---|
| 論点は3つ | 4つ以上に増やさない。増えたら統合するか捨てる |
| 論点の出所 | ヒアリングで**2回以上出た言葉**から取る。こちらの都合で作らない |
| 論点の構造 | 各論点に「現在地／本提案／該当章」の3点を必ず持たせる |
| 章の帰属 | すべての可変スライドは3つの論点のいずれかに属する。属さないスライドは削る |
| サマリーは最後 | P2は全章確定後に書く。先に書くと章が論点から離れても気づけない |
| 参照列の更新 | 章を増減したら論点表の参照列を更新する。**更新漏れ＝提案の破綻** |

### 論点表の型（P5）

| | 論点01 | 論点02 | 論点03 |
|---|---|---|---|
| 見出し | どこで◯◯と出会うか | 何を伝えるか | どうつくり、どう運用するか |
| 現在地 | 事実で書く。評価しない | 同左 | 同左 |
| 本提案 | 打ち手を1文で | 同左 | 同左 |
| 参照 | 2・3・5章 | 3・6章 | 7・8章 |

## 特記事項（社内の政策ルール）

`references/policy-rules.md` に蓄積する。**提案書を作るとき・レビューするとき、必ず読み込む。**

### 反映先は必ず4カ所のどれか

| 反映先 | 該当スライド | 使い分け |
|---|---|---|
| A. よくあるご質問 | P92（章13） | 先方が疑問に思う前に先回りして答える内容 |
| B. 本提案の前提 | P7（章01） | 提案全体の土台になる認識合わせ |
| C. ご契約諸条件 | P93（章13） | 支払・責任・権利など契約に属する内容 |
| D. 見積書側の注記 | 提案書外 | 金額の内訳・除外範囲に属する内容 |

反映先が決まらないルールは登録しない。**書いたが提案書に出ない**状態を作らないための制約。

### ルールを追加するとき

`references/policy-rules.md` の記述フォーマットに従って追記する。
ID採番・反映先の指定・記載文案の3点が揃っていなければ登録しない。

## 品質チェックリスト（提出前）

### 構成
- [ ] 3つの論点が確定し、P2・P5・各章で一致している
- [ ] 論点表の参照列が実際の章番号と合っている
- [ ] 「本提案の前提」に、認識違いが起きうる項目が漏れなく載っている
- [ ] 可変スライドがすべて3つの論点のいずれかに属している

### 特記事項
- [ ] `policy-rules.md` の全ルールを確認した
- [ ] 反映先A（FAQ）のルールが提案書のFAQに載っている
- [ ] 反映先B（前提）のルールが「本提案の前提」に載っている
- [ ] 見積と提案書で制作範囲の記述が矛盾していない

### 文言・数字
- [ ] すべての数字に出所と調査時点がある
- [ ] 効果予測がレンジで書かれている（単一値の断定がない）
- [ ] 仮案・仮設定に「仮」と明記されている
- [ ] リード文がすべて「です・ます」
- [ ] 先方の言葉を勝手に言い換えていない

### 版面
- [ ] 全ページにフッター `NN|総ページ数` がある
- [ ] 章扉が 通番／英ラベル／日本語章名 の3点セットになっている
- [ ] 別紙への参照が明記されている（デザイン・WF・仕様書）
