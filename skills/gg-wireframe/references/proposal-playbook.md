# 提案・コンペでの使い方

## 1. GrowGroupの提案フローの中での位置づけ

社内の営業フローは
**お問合せ → アポイント → ヒアリング → 提案・見積（プレゼン） → クロージング → 成約可否**。
仕様書は 表紙／お客様情報／初回ヒアリング／仕様／制作比率／SEOキーワード調査／
**提案サイトマップ**／スケジュール で構成される。

HTMLワイヤーは「提案サイトマップ」の次に置く**構成の証拠物件**として機能する。
サイトマップは合意を取る道具、ワイヤーは差をつける道具、と役割が違う。

案件確度が高い、または競合コンペの場合にワイヤーまで踏み込む。
確度が読めない初回提案ではサイトマップ＋TOPワイヤー1枚に絞る。

## 2. 何ページ作るか

| 状況 | 作る範囲 | 目安工数 |
|---|---|---|
| 初回提案・確度不明 | TOPのみ | 半日 |
| コンペ（標準） | TOP＋主要下層2〜3ページ＋サイトマップindex | 1〜2日 |
| コンペ（大型・複数サイト） | 各サイトのTOP＋主要下層 | 3日〜 |
| 受注後の設計フェーズ | 全ページ | 別フェーズとして見積 |

**全ページ作らないこと。** 提案段階での網羅は評価されず、
「TOPと、その提案の肝になる1〜2ページ」に密度を集中したほうが勝率が上がる。
肝になるページの選び方は、コンペ要項の「追加課題」や
ヒアリングで先方が繰り返した不満点から特定する。

## 3. 松竹梅との紐づけ

ワイヤーは1本作り、**注釈でプラン差分を示す**のが最も効率的。

```html
<div class="wf-note" data-n="5">
  <b>意図</b>課題別の入口を新設。指名検索以外の流入を受け止める。
  <br>【梅】カテゴリ4つの静的ページ／【竹】CMS化し追加可能／【松】診断コンテンツと連動
</div>
```

セクションごと丸ごとプラン差がある場合は、そのセクションの注釈冒頭に
`【竹以上】` と書いてから内容を記す。ワイヤーを3本作る必要はない。

## 4. プレゼンでの見せ方

**画面共有で実物を触る。** これがHTMLワイヤーの最大の価値。
PDFやスライド画像に落とすと、Figmaや他社のスライドと同じ土俵に戻ってしまう。

進め方：

1. `index.html`（サイトマップ）から開始。全体像と各ページの役割を説明
2. TOPページへ遷移。**注釈ONのまま**、上から順に「なぜこの順序か」を説明
3. SPボタンを押して切り替える。ここで必ず反応がある
4. 注釈OFFにして「これが構成そのもの」を見せる
5. 主要下層ページへ遷移。回遊が成立していることを見せる

**SP切替は必ず見せ場として使う。** 会議中にレイアウトが実際に組み替わるのは
静止画の提案では起こせない体験で、「ちゃんと考えている」という印象を作る。

## 5. 提案書（PPTX）への埋め込み

プレゼン後に残る資料には静止画が必要。手順：

1. 注釈ONの状態でPCとSPをそれぞれフルページスクリーンショット
2. 縦長なので、提案書には「FV〜3スクロール目」までのトリミングを貼る
3. 全長版は別紙またはPDFで添付
4. スライド本体には**構成の意図を3〜4点の箇条書き**で併記する

画像だけ貼っても伝わらない。必ず「なぜこの構成か」を言語で残す。

## 6. 納品時の注意

- HTMLはフォルダごとZIPで渡すか、ステージング環境にアップして限定URLで共有
- 相対パスで組む（`href="service.html"`）。ローカルでダブルクリックしても動くこと
- ファイル名は英小文字とハイフンのみ。日本語ファイル名は環境依存で壊れる
- 先方社内で回覧される前提で、**冒頭に「これはデザインではなく構成案です」と明記**する
  ツールバーの `wf-bar__meta` にその旨を書いておくと事故が減る

## 7. モノクロを崩さないための判断基準

「ここだけ色を入れたい」は必ず出てくる。以下で線を引く。

| 要望 | 対応 |
|---|---|
| CTAを目立たせたい | 色ではなく、面積・位置・余白で強弱をつける。`wf-btn--lg` を使う |
| ブランドカラーを見たい | ワイヤーでは入れない。デザインフェーズの議題として切り分ける |
| 重要度の差を示したい | グレーの濃淡（`--wf-solid` と `--wf-btn--ghost`）で表現する |
| 注釈を目立たせたい | ここだけ `--wf-note` の使用を許可 |

**モノクロにする理由をクライアントに説明できるようにしておく。**
色が入ると人は色の話をする。構成の合意を取るべき場で装飾の議論が始まると、
デザインフェーズでの手戻りが増える。モノクロは議論の焦点を守るための装置。

## 8. 品質チェックリスト

提出前に必ず全項目を確認する。

### 構成
- [ ] FVから3スクロール以内で「何の会社／何の募集か」が分かる
- [ ] グローバルナビが6項目以内
- [ ] 全ページの末尾にCTAバンドがある
- [ ] 主CTAと副CTAの2種類がある（BtoBは資料DL、採用は説明会予約が定番）
- [ ] 一覧ページに絞り込み軸が4〜5軸ある
- [ ] 見出し階層が h1→h2→h3 の順で飛んでいない
- [ ] 各ページに固有の h1 が1つだけある

### 表示
- [ ] PC（1280px）で崩れていない
- [ ] SPボタンで切り替えて崩れていない（これを飛ばさない）
- [ ] SP時に固定CTAが出ている
- [ ] SP時にグローバルナビがバーガーに変わっている
- [ ] テーブルがSPで縦積みになっている
- [ ] 画像枠に斜線クロスが出ている

### 注釈
- [ ] すべての注釈に `data-n` の通し番号が振られている
- [ ] ラベルが 意図／根拠／差別化／要確認 のいずれかに統一されている
- [ ] 注釈OFFにして、ワイヤー単体で構成が読めるか確認した
- [ ] 「要確認」がクライアントへの宿題として整理されている

### リンク
- [ ] index.html から全ページに遷移できる
- [ ] 各ページから index.html に戻れる
- [ ] 未実装リンクは `href="#"` で統一されている（リンク切れを作らない）

### 文言
- [ ] ダミーテキストが大量に残っていない（実コピー案を書く）
- [ ] 他案件のクライアント名が残っていない
- [ ] 「ここに〜が入ります」だけのブロックがない

### 汎用性
- [ ] `wireframe.css` を1文字も編集していない
- [ ] ページ側に `<style>` を書いていない
- [ ] インラインスタイルが3箇所以下

最後の3つを守ると、次の案件でCSSをそのまま流用できる。
これが「案件ごとに作り直さない」ための唯一の条件になる。
