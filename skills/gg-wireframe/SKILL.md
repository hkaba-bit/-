# モノクロHTMLワイヤーフレーム構築

## このスキルが解く問題

提案・コンペの場で、Web制作会社の差は「デザインの綺麗さ」ではなく
**「構成をどれだけ具体的に見せられるか」**で決まる。
クライアントは「構成イメージを見せてくれる会社」を評価する。

このスキルは、無彩色で装飾を排したHTMLワイヤーを短時間で組み立て、
画面共有で実際に触りながら構成の合意を取るための道具一式を提供する。

**モノクロである理由**：色が入ると人は色の話をする。
構成の合意を取るべき場で装飾の議論が始まると、デザインフェーズでの手戻りが増える。
モノクロは議論の焦点を「情報設計」に固定するための装置。

## 参照ファイル

作業に入る前に、該当するものを読む。

| ファイル | いつ読むか |
|---|---|
| `references/patterns-corporate.md` | コーポレート／BtoBサービスサイトを作るとき |
| `references/patterns-recruit.md` | 採用サイトを作るとき |
| `references/components.md` | HTMLを書き始めるとき（毎回） |
| `references/proposal-playbook.md` | 提案での見せ方・松竹梅連携・品質チェックのとき |

| `assets/_page-template.html` | 各ページの起点にする雛形 |
| `assets/example-corporate-top.html` | 完成例（BtoB製造業のTOP）。密度と注釈の書き方の基準として最初に見る |

## ワークフロー

### STEP 1. 与件を確定する

以下が埋まらないと構成は決められない。不明な項目は推測で埋めず、
「要確認」として注釈に残し、提案時にクライアントへの質問として提示する。

| 項目 | 確認すること |
|---|---|
| サイト種別 | コーポレート／BtoBサービス／採用（新卒・キャリア）／複合 |
| 目的・KGI | 問い合わせ増／リード獲得／エントリー数／認知 |
| ターゲット | 誰が、どんな課題を持って、どこから来るか |
| 主CV・副CV | 問い合わせ／資料DL／エントリー／説明会予約 |
| 主要デバイス | 採用は原則SP主体。BtoBはPC寄りだが調査で確認 |
| 現行サイトの不満 | ヒアリングで先方が繰り返した言葉をそのまま拾う |
| 競合 | コンペ相手ではなく、クライアントのビジネス上の競合 |
| 予算・プラン | 松竹梅のどこに何を入れるか |

現行サイトがある場合は必ず実際に見る。ヒアリング議事録があれば、
**先方が繰り返した不満の言葉**を特定する。それが提案の肝になるページを決める。

### STEP 2. サイトマップを確定する

`patterns-corporate.md` または `patterns-recruit.md` の型を土台にし、
案件固有の事情で足し引きする。この段階で決めること：

- ページID（`top` / `service` / `service-detail` など。英小文字とハイフン）
- 階層（第2階層は6項目以内。超えたら情報設計を疑う）
- 各ページの役割を1行で
- 提案で実際にワイヤーを作るページの選定

**ワイヤーは全ページ作らない。** TOPと、提案の肝になる1〜2ページに密度を集中する。
網羅は評価されない。

### STEP 3. ページ別の設計を書き出す

HTMLを書く前に、各ページについて以下を文章で確定させる。
ここを飛ばすと、コンポーネントを並べただけの中身のないワイヤーになる。

```
【ページID / ページ名】
目的：
このページで解決する疑い：
掲載ブロック：（上から順に列挙）
主CTA / 副CTA：
SP時の注意点：
要確認事項：
```

### STEP 4. HTMLを組む

1. 作業ディレクトリに `wireframe.css` をコピー
2. `index.html`（サイトマップ兼ハブ）を作る
3. 各ページを `_page-template.html` から起こす
4. `components.md` のスニペットを組み合わせて本文を構築
5. 注釈を入れる

**ファイル構成**
```
{クライアント名}_wireframe/
├── index.html          サイトマップ兼ハブ（ここから全ページへ）
├── wireframe.css       共通CSS（編集しない）
├── top.html
├── service.html
└── recruit-top.html
```

すべて相対パス。ローカルでダブルクリックしても動くこと。
ファイル名は英小文字とハイフンのみ。日本語ファイル名は環境依存で壊れる。

### STEP 5. 検証する

`proposal-playbook.md` の品質チェックリストを全項目確認する。
特に **SPボタンを押して崩れを確認する工程を飛ばさない**。

### STEP 6. 提出する

`present_files` でHTMLとCSSをまとめて渡す。
提案での見せ方は `proposal-playbook.md` を参照。

## 実装の規約

### 絶対に守る3点

1. **`wireframe.css` を編集しない**
2. **ページ側に `<style>` を書かない**
3. **インラインスタイルは3箇所以下**

この3つを守ると、次の案件でCSSをそのまま流用できる。
守らないと案件ごとに作り直すことになり、スキルとして成立しなくなる。

足りないパーツが出たら、まず `components.md` の組み合わせで解けないか疑う。
本当に汎用的な不足であれば、その案件を終えてから `wireframe.css` に追記する。

### 色

`wireframe.css` の10段階グレースケールのみ使う。
有彩色は注釈用の `--wf-note` だけ。ワイヤー本体には一切使わない。

強弱は色ではなく**面積・位置・余白**でつける。
主CTAは `wf-btn--lg`、副CTAは `wf-btn--ghost` で差をつける。

### レスポンシブ

**メディアクエリを使わない。コンテナクエリを使う。**

```css
@container (max-width:600px){ ... }   /* 正しい */
@media (max-width:600px){ ... }       /* 使わない */
```

`.wf-canvas` に `container-type:inline-size` が設定されており、
SP切替ボタンでキャンバス幅が390pxになると `@container` が発火して
**実際にレイアウトが組み替わる**。メディアクエリはビューポート基準なので発火しない。

これが会議中の見せ場になる。静止画の提案では起こせない体験なので必ず使う。

### プレースホルダ

| 用途 | 書き方 |
|---|---|
| 画像 | `<div class="wf-img wf-img--wide"><span>IMAGE</span></div>` |
| アイコン | `<div class="wf-img wf-img--icon"><span></span></div>` |
| 未確定の本文 | `<div class="wf-dummy"><span></span><span></span></div>` |

**コピーは実案を書く。** `wf-dummy` の多用は避ける。
提案用ワイヤーでは、見出しとCTAラベルに実際のコピー案を書いたほうが必ず刺さる。
「ここにキャッチコピーが入ります」で埋めたワイヤーは評価されない。

### 日本語組版

- 行間 1.8（`wireframe.css` で設定済み）。1.5以下にすると窮屈に見え、実装も窮屈になる
- 本文16px相当が基準。ワイヤーで小さく作ると実装も小さくなる
- 見出しの改行位置は `<br>` で明示する。日本語は改行位置で印象が変わる
- 縦長ページは許容される。無理に情報を削るより、順序を正すことを優先する

### フォーム

入力欄は `input` ではなく `div.wf-input` で作る。
ワイヤーで実際に文字が打てると、クライアントの意識が「動くかどうか」に逸れて
構成の議論が止まる。

## 注釈のルール

注釈こそが提案の中身。ワイヤーの図だけでは差はつかない。

```html
<div class="wf-note" data-n="3">
  <b>根拠</b>現行サイトの直帰率が72%。FV直下で課題提起し離脱を止める。
</div>
```

- `data-n` はページ内の通し番号。1から振る
- `<b>` のラベルは次の4種に統一する

| ラベル | 書く内容 |
|---|---|
| 意図 | このブロックが担う役割・なぜこの位置か |
| 根拠 | データ／ヒアリング／競合分析のどれに基づくか |
| 差別化 | 競合がやっていないこと |
| 要確認 | クライアントに決めてもらう必要がある事項 |

**注釈OFFで構成が読めることを必ず確認する。**
注釈がないと意味不明なワイヤーは、ワイヤーとして失敗している。

松竹梅のプラン差は注釈内に書く。ワイヤーを3本作らない。
```
【梅】静的4ページ／【竹】CMS化／【松】診断コンテンツ連動
```

## index.html（サイトマップ兼ハブ）

提案は必ずここから始める。全体像を見せてから各ページに降りる。

```html
<section class="wf-sec">
  <div class="wf-inner">
    <h1 class="wf-h1">サイトマップ</h1>
    <p class="wf-lead">全◯ページ構成。網掛けは今回ワイヤー作成済みのページ。</p>

    <h2 class="wf-h2">コーポレートサイト</h2>
    <div class="wf-grid wf-grid--3">
      <a href="top.html" class="wf-navcard">TOP</a>
      <a href="service.html" class="wf-navcard">サービス</a>
      <span class="wf-navcard" style="opacity:.5">導入事例（未作成）</span>
    </div>
  </div>
</section>
```

ページ数と階層が一目で分かること、
ワイヤー作成済みと未作成が区別できることの2点を満たす。

## 判断に迷ったときの原則

| 迷い | 判断 |
|---|---|
| ページを増やすか、1ページを長くするか | 目的が違うなら分ける。同じ目的なら長くしてよい |
| 情報を削るか、順序を変えるか | まず順序。削るのは最後 |
| 網羅するか、絞るか | 提案では絞る。密度を肝のページに集中させる |
| 実コピーを書くか、ダミーにするか | 見出しとCTAは実コピー。本文はダミー可 |
| 色を入れたいと言われたら | 入れない。デザインフェーズの議題として切り分ける |
| 全ページ作れと言われたら | 設計フェーズとして別途見積もる旨を提示する |

## やってはいけないこと

- `wireframe.css` を案件ごとに書き換える（流用できなくなる）
- メディアクエリでレスポンシブを組む（SP切替が機能しなくなる）
- 装飾・配色・写真の雰囲気で見せようとする（ワイヤーの目的から外れる）
- ダミーテキストだけでページを埋める（提案として評価されない）
- 注釈なしで提出する（構成の意図が伝わらない）
- 全ページ作って提案工数を溶かす
- 他案件のクライアント名や固有名詞を残したまま提出する
